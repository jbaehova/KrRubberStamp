# VAT와 문서 추출 통합 감사

이 보고서는 개별 집필 전환 전에 수행한 기반 엔진 및 보조 생성기 감사 이력이다. 최종 개별 집필 원고와 원자료 연결 계약을 감사했다는 뜻은 아니다. 아래 당시 내보내기 제한과 생성 범위는 당시 상태를 기록한 것이다. 개별 집필본의 현재 측정은 배치 보고서와 별도 편집 감사로 확인한다.

감사일: 2026-10-09. 코드 수정 없이 `reports/audit_vat_extract.md`와 `tmp/audit/` 안에서만 증거를 기록했다. 감사 범위는 C와 D 규칙, 문항 계약, 품질 게이트, 채점기, 하네스, 배치 생성 및 HF 내보내기였다. A와 B의 세법 계산 및 최종 1,200문항 검증은 루트 작업의 별도 범위다.

## VAT 근거와 계산

[국세청 도소매업 원본 PDF](https://www.nts.go.kr/comm/nttFileDownload.do?fileKey=95e20f2fcbd5b8094e3899abd6609bc2)와 [화물운수업 원본 PDF](https://www.nts.go.kr/comm/nttFileDownload.do?fileKey=4548e87d3b83680b1052815001597b9d)를 독립적으로 내려받았다. 두 파일 모두 fixture에 기록된 SHA-256과 일치했다. 원본 2쪽과 3쪽을 이미지로 렌더링해 17개 공급가액 및 세액 항목과 완성 신고서를 확인했다.

도소매업 과세표준 105,000,000원과 매출세액 10,500,000원이 일치한다. 공제 가능한 매입세액 7,700,000원에서 계산되는 납부세액 2,800,000원에 발행세액공제 200,200원과 예정고지 1,500,000원을 차감한 1,099,800원이 원본과 같다. 화물운수업은 매출세액 4,000,000원에서 매입세액 1,550,000원과 예정고지 1,200,000원을 차감한 1,250,000원이 일치한다.

[국세청 공식 안내](https://www.nts.go.kr/nts/cm/cntnts/cntntsView.do?cntntsId=239004&mi=40574)의 현행 표시에서 2026년 말까지 1.3%와 연간 1,000만원 한도를 확인했다. 법인과 직전년도 사업장별 공급가액 10억원 초과 개인사업자 제외도 확인했다. 이 감사에서 국가법령정보센터 조문 팝업은 본문을 반환하지 않아 법령 전체를 새로 독립 확인하지는 못했다.

생성 범위인 국내 10% 과세 일반과세자 거래에서 새로운 금액 계산 결함을 발견하지 않았다. 거래 ID 중복 시 증빙을 합치고 세금계산서 발급 거래를 영수증 발행 공제에서 제외하는 구현은 공식 중복 사례와 일치한다. 공제액의 납부세액 한도와 예정고지 차감 순서도 구현 및 fixture에 일관되게 적용된다.

공식 숫자 자료는 17개 표 항목과 완성 사례 2개다. 17개의 독립적인 완성 신고 사례로 표현하면 안 된다. 법령을 확인했지만 독립 공식 숫자 사례를 확보하지 못한 불공제 및 공제 한도 규칙의 `verified: false` 표시는 적절하다. 과면세 공통매입 안분과 영세율 및 가산세 제외도 명시된 범위 제한이다.

## 검증 증거

- `uv run pytest tests/test_vat.py tests/test_extract.py tests/test_grader.py tests/test_harness.py tests/test_task_contract.py tests/test_quality.py --basetemp tmp/audit/pytest_final`: 82 passed. PyMuPDF의 기존 SWIG deprecation warning 5개만 존재.
- 현재 코드로 C와 D 각각 easy, medium, hard 문항을 새로 렌더링함. 6문항과 입력 파일 34개가 품질 검증을 통과함. `tmp/audit/release_probe/source/batch_1/`에 보존함.
- 같은 6문항의 oracle exact_match와 field_accuracy는 각각 1.0. null은 둘 다 0.0. 모델 HTTP POST를 실패하도록 차단한 상태에서 가짜 솔버를 실행함.
- 실제 D 문항의 oracle 실행 중 gold.json과 trace.json에 대한 Path.read_text 및 Path.read_bytes를 차단해도 계산 정답이 같았음. 추출 맵에는 파일 위치 및 자료형이 있고 값은 실제 PDF 텍스트와 XLSX 셀 및 HWPX XML에서 읽음.
- 사업자번호 10,000개를 생성해 표준 체크섬을 독립 계산함. 10,000개 모두 고의로 무효한 체크섬을 가짐.
- 배치 생성의 제어 흐름을 임시 대체 생성기와 렌더러로 검사함. 첫 품질 탈락 후 재시도는 4문항을 채우며 실제 문항 폴더와 gold 개수도 각각 4개. 영구 품질 탈락은 25회 기록 후 RuntimeError를 내고 무효 task.yaml 및 gold를 남기지 않음.
- 이전 batch_* 형제 폴더의 동일 시나리오 해시를 주입한 검사에서 중복 후보 1개를 제외한 뒤 4개의 고유 문항을 생성함. 이 제어 흐름 검사는 실제 세법 계산 검증을 대체하지 않음.

## 내보내기와 남은 통합 확인

6문항 HF JSONL은 생성되었고 모든 입력 경로가 존재했다. gold와 answer_schema 및 trace JSON 문자열도 파싱된다. 다만 감사 실행 시점에는 루트 규칙 레지스트리 `rules/sources.yaml`이 아직 없어서 export_hf의 마지막 복사 단계가 FileNotFoundError로 종료되었다. 이 파일은 별도 통합 작업의 의존성이므로 최종 배치 내보내기 전에 생성하고 export-hf를 다시 실행해야 한다. 현재 감사의 부분 내보내기는 최종 배포 산출물로 사용하면 안 된다.

프로젝트 환경에 datasets 패키지가 없어 Hugging Face의 Arrow 로더 자체는 실행하지 않았다. JSONL 구조와 경로 및 JSON 문자열만 검사했다. 전체 1,200문항의 최종 gate 결과와 배포 카드, 최종 내보내기 성공은 루트 검증 대상이다. PNG는 PDF 사본으로 제공되므로 스캔 단독 OCR 검증으로 주장하면 안 된다. HWPX의 한컴 앱 호환성도 이 감사에서 확인하지 않았다.

감사자가 변경한 추적 대상 경로는 이 보고서 하나다. 모델 API 호출과 데이터 업로드는 수행하지 않았다.
